# K230 前视视觉调试

本目录保存亚博 K230 的前视识别程序与调试记录。Ti60 为整车主控，后置 OV5640 接 Ti60。

当前赛场前视入口和部署方式见 [现场前视版](#现场前视版)。

2026-11-18 独立程序：

- [现场连拍 v1.5](field_capture/README.md)：720p 每 250 ms 采样，写入 `/data/field_photos`；用户确认实机采样可用。
- [左右转识别](turn_verify/README.md)及 [Ti60 两板联调](turn_link/README.md)：用户确认台架左右转方向已接通；整车过分岔待验证。

v1.6.1 已统一为 Ti60 现有的三位数据+STB协议，固定接线见
[K230_GPIO_FIXED.md](../docs/K230_GPIO_FIXED.md)。GPIO 默认关闭，首次接线前仍需运行时占用审计及电平测量。
下方 REQ/ACK 内容属于旧版本，不再作为接线依据；原 v1.6 归档说明见 [归档状态](ARCHIVE_STATUS.md)。

### v1.6.1 固定 GPIO 通信

- DATA0/1/2=GPIO42/43/34，STB=GPIO35，不使用 ACK、GPIO32/33/26。
- 分别接 Ti60 P4 pin28/33/34/39；K230 排针 pin4 接 Ti60 pin30 共地。
- 发送完整两遍符号帧，每次至少30ms，空闲约500ms发心跳；该实现会短暂阻塞预览。
  启用后的实际帧率需要测量，GPIO_ENABLE=False 时不产生发送开销。
- 摄像头和显示运行后输出 `[PIN-AUDIT]` 并存入SD日志。启用GPIO时遇到其他外设复用会拒绝抢占。
- 日志 `frame_sent_no_ack` 表示已发送，不是对方确认；GPIO记录改为 STB、累计发送帧数。
- GPIO本身不能证明物理电压；若K230输出1.8V，在固定四根线上加适当电平转换，编号不改。
- 桌面检查命令：`python k230/tools/check_gpio_link.py`；加 `--rtl --iverilog-dir <bin目录>` 可回放
  真实发送端生成的引脚时序到现有 `src/k230_link.v`。未增加屏幕驱动，尚未烧板。

## 第一版使用说明

### v1.6 多目标顺序与自动 SD 记录（当前版本）

把 ZIP 中的 `car_vision` **整个文件夹覆盖到 SD 卡根目录**，保留其他目录、历史照片及
已有启动入口，然后重启板卡。新增 `multi_tracker.py`、`run_recorder.py`，只替换 main.py
会缺少模块。仍默认箭头模式，点右侧“模式”切换到颜色模式；自动记录不需要另外开启。

颜色模式允许同时跟踪多块目标，每块分配编号，同色的两块也分别跟踪。
先在左侧稳定看到目标，再根据目标向右越过两条门线的过程判断经过顺序：

1. 初始观察区为原始 640×360 图像的 `(32,36,608,306)`；面积至少 500 像素、
   稳定至少 250 ms 且至少 3 次有效观察后确认。这些是现场标定前的起步值。
2. 完整目标中心在准备线左侧（x≤460.8）时进入待计数状态；随后向右移动至少 55 像素，
   中心越过计数线（x=563.2），并在其附近或右侧保持至少 140 ms、2 次观察后计数。
   比较插值得到的越线时间，避免用“某次检测突然丢失”直接决定先后。
3. 轻微回摆允许 8 像素容差；越线后回摆不会重复计数。短时遮挡保留编号，默认最多 800 ms。
   新出现时已在准备线右侧的目标不会直接计数，需要先有完整的准备过程。
4. 多目标同时发生明显横向跳动、目标关联有歧义、两块越线时间接近到无法可靠区分，
   会暂缓或拒绝计数，并保存原因。已准备目标丢失或越线存在歧义时显示“顺序待复核”。
   整体运动判断只是启发式保护，不能可靠分离所有循迹扭动与正常前进。
5. 画面显示目标编号、颜色、框和两条门线。下方只保留本轮前四次有效事件；后续事件仍记日志。
   “清序”重置本轮；切换模式、浏览相册后重新建立轨迹，保留已记录顺序，不推断暂停期间经过了什么。

`config.py` 中 `TRACK_*` 调整区域、门线、确认、容差与遮挡时间；`COLOR_LAB`、
`COLOR_MIN_PIXELS` 调整颜色与尺寸。现场先固定相机角度，利用记录中的目标像素大小、
移动速度和失检情况再调参。没有声称这些默认值已经适配比赛速度或实际车身摆动。

每次运行自动建立以下目录，路径中的会话编号递增：

```text
/sdcard/car_photos/session_0001/
  00001_unknown.jpg           人工拍摄的 1280×720 原片
  index.jsonl                人工照片标签与识别结果
  events.jsonl               兼容原有事件记录
  analysis/
    manifest.json            固件、参数、坐标说明
    source/                  本次部署的 11 个运行源码副本
    frames_0001.jsonl        逐帧测量、事件与操作；每约 4 MiB 分卷
    images/frame_00000000.jpg 640×360 原始预览截图，不带界面
```

- 逐帧保存全部保留的候选色块、过滤原因、候选溢出数量、轨迹编号/框/速度/状态、
  越线事件、本地顺序、歧义与丢失原因、GPIO 状态、帧率、分段耗时和人工照片引用。
  启动、切模式、清序、浏览、拍摄操作、异常及退出也会记录。GPIO 默认关闭；
  v1.6历史日志的 `accepted_for_handshake` 只表示进入旧握手；v1.6.1改用 `frame_sent_no_ack`，均不证明接收成功。
- 默认每秒存一张 640×360 JPEG；计数或轨迹异常时尝试加存关键帧，最小间隔 250 ms。
  所以这是**逐帧测量加抽样图片，不是完整视频**。人工拍照/连拍仍保存 1280×720。
  `LOG_IMAGE_INTERVAL_MS` 和 `LOG_EVENT_IMAGE_GAP_MS` 可调整；更频繁写卡会影响帧率。
- 每个会话的 analysis 默认最多 128 MiB，SD 剩余不足 32 MiB 或写入失败则停止自动记录，
  屏幕提示“SD记录停止”，终端输出原因；识别继续运行，旧记录不自动删除。
  停止时尝试追加一条很小的故障原因记录，可略超分析限额；实际卡故障时该记录也可能写不进去。
  这一限额不包含人工高清照片和原有索引；人工拍摄沿用自己的 16 MiB 空间保护。
- 普通记录每 8 条或约 500 ms 刷入文件，每约 2 秒尝试文件系统同步；计数事件、
  操作及正常退出立即同步。突然断电仍可能丢失末尾缓冲或损坏日志行，不保证零丢失。
  取卡前点“退出”，等待程序停止。相册浏览期间暂停采集，不会产生实时逐帧记录。
- 文件与运行时间使用会话号、帧号和 ticks，不依赖未校准的 RTC；轨迹内部另有经过时间。
  主程序启动时会打印 `[RENDER] v1.6 multi-target gates + SD analysis recorder`。

回到电脑后复制**整个 session 目录**，用包中的电脑工具导出轨迹 CSV 与事件摘要：

```powershell
python desktop_tools/analyze_run.py "D:/k230_samples/session_0001"
# 在本仓库运行时使用：
python k230/tools/analyze_run.py "D:/k230_samples/session_0001"
```

结果在 `analysis/report/tracks.csv`、`summary.json`。摘要包含计数、歧义、性能、操作、
异常和是否见到结束记录；遇到损坏/截断行会报告文件及行号，继续读取其他记录。
该工具整理原始测量，不自动证明实际顺序正确；分析时同时查看 images 和人工照片。

台架先用两块同色和两块异色物体，从准备线左侧缓慢移到右侧；再试回摆、短暂遮挡、
同时移动和相册返回。核对屏幕编号/计数与 SD 日志，并观察 PERF 新增 `log` 耗时。
29 项桌面检查和语法检查通过，覆盖轨迹、记录限额与损坏日志处理；摄像头、LAB 与 SD
硬件接口使用替身，不能代替本版实机验证。新增记录后的实际帧率尚未测量。

- 下方显示本轮前四个颜色事件的**本地诊断顺序**，允许重复色；右侧“清序”清空它并重置
  颜色事件锁存。此按钮仅清理 K230 台架记录，不是 Ti60 的比赛复位命令。
  超过四项时诊断显示冻结，但后续真实经过事件仍可上报，由 Ti60 最终管理比赛记录。
- 蓝色候选额外检查内部白色箭头模板，尽量排除交通标识；不保证所有距离、角度都能排除，
  正式使用还需结合观察区域和 Ti60 比赛阶段防止蓝色标识误记为蓝色色块。
- `events.jsonl` 按事件保存模式、颜色/箭头、GPIO 编码、候选信息和本地顺序；
  照片索引同步保存拍照时模式、本地顺序和该照片自身的识别结果。人工照片标签仍独立选择。
- GPIO 协议保持 1 左、2 右、3 红、4 绿、5 蓝、6 黄。GPIO_ENABLE 默认关闭；
  接收端尚未验证，未声称已能控制 Ti60。若开启时发送忙/失败，终端会提示，不静默当作已发送。
- 右侧现在为“场景 / 模式 / 清序 / 退出”，左侧仍为“拍照 / 连拍 / 相册 / 标签”。
  相册中左右翻页、返回预览保持原操作。浏览暂停不作为目标离开证据。

桌面颜色检查七组通过，原有原型检查六组通过；其中 LAB 查找和硬件部分用替身验证流程，
不代表实际颜色准确率。阈值只是起步值，需要用 K230 实拍调参，新增颜色模式帧率也需实测。
拍照/回看曾由用户确认可用，但本版仍需回归这两项。

不移动车辆的验证方法：
1. 点“模式”进入颜色模式，用红色物体完整放进黄框，停留约一秒，应记录一个“红”。
2. 保持不动数秒，不应继续重复记录。
3. 将目标完全移出黄框约一秒，再放回红色物体，应得到“红-红”。
4. 清序后依次放入红、绿、蓝、黄，每次之间移开约一秒，检查顺序及终端 `[EVENT]`。
5. 在框内同时放两种面积接近的色块，以及蓝色箭头牌，检查拒识/误报情况；
   拍摄这些失败场景，便于后续调整阈值、观察区和标识排除。

### v1.4.4 分段性能诊断

用户反馈完整应用约 7.3 FPS。此版每约三秒在终端输出一条 `[PERF] ms/frame`，
分别统计 capture（预览采集等待）、detect（识别）、photo（本窗口内拍照总耗时摊到每帧）、
compose（格式转换与居中拷贝）、ui（透明背景和文字）、show（显示提交）、gc（垃圾回收）、
other（其余流程）及 total。计时不包含相册停留，回到实时后重新开始。
显示提交耗时不等同于屏幕物理刷新延迟。采集双通道和显示方式保持不变，
先取得实机分段数据，再决定优化；此版不宣称帧率提升。只需替换 main.py。

### v1.4.3 预览帧率

顶部右侧显示应用预览 FPS，按每个不少于一秒的窗口统计完成的循环数/实际时间，
包括采集、识别、拍照写卡（如发生）、画面合成、显示提交与垃圾回收耗时。
不是传感器原生帧率，也不是屏幕物理刷新率。首次统计前显示 `-- FPS`。
相册不显示实时 FPS，从相册返回后重新统计，避免把浏览停留时间算入预览。
仅需更新 main.py。此版加入测量，没有声称已解决低帧率。

### v1.4 等比例预览与高清采样

- 屏幕保持 640×480；通道 1 输出 640×360 RGB565 做识别。

- **需要同时替换 `car_vision/main.py` 和 `car_vision/config.py`**，其他运行文件保持。

### 屏幕操作

- **拍照**：保存高清通道完整 1280×720 原始画面，不带边框、按钮或识别文字。
- **标签**：循环选择 `unknown / left / right / negative / red / green / blue / yellow`。
  分别表示未知、左箭头、右箭头、无目标负样本、红、绿、蓝、黄。标签由人确定，
  不随预测结果变化；拍右箭头前选择 `right`，即使识别错了也仍保存真实标签。
- **场景**：循环 `normal / far / near / tilted / dim / glare / moving / background`，
  对应普通、远、近、倾斜、暗、反光、运动、背景。此字段用于后续筛选样本。
- **连拍/停**：默认每秒一张，共 10 张；再次点击取消。连拍期间标签和场景锁定为启动时的选择。
  进入相册或点击实时也会取消连拍。
- **相册**：查看当前和以前启动时拍的照片，上一张/下一张切换；返回或实时回到预览。
  原片不会被相册界面覆盖，也没有删除按钮。
- **退出**：结束程序并释放摄像头、显示资源。重启板卡可重新运行自启动程序。
- **实体 KEY**：短按拍一张，长按至少 0.8 秒后松开切换标签；不要按 RST。
  实体按键在相册中不执行拍照。无屏版本可用长按选择标签，观察 IDE 输出。

上电预热 2 秒后才接受拍摄和箭头确认。UI 使用英语标签简写便于导出数据，按钮为中文。
连拍是按“保存完成后再等待一秒”安排，实际间隔可能略大于一秒，不是严格定频录像。

### 保存位置与取回

照片在 `/sdcard/car_photos/session_0001/` 等目录，每次运行递增会话号，避免重启后覆盖。
每张 JPEG 文件名包含序号和人工标签；同目录的 `index.jsonl` 记录人工标签、场景、预测、
匹配分数、候选框、帧号与运行时间。`settings.json` 保存主要识别参数。
运行时间不是可靠的日历时间，目录也不依赖板卡 RTC。

保存完成且没有正在连拍时再退出程序、断电取卡；也可以用 CanMV 文件管理复制整个
`car_photos` 目录。电脑上的采样副本建议放仓库已忽略的 `data/k230/` 下，避免入 Git。
剩余空间不足 16 MiB 或写入失败时会显示错误并停止连拍；卡里已有照片不会自动删除。
如果 JPEG 成功但索引写入失败，照片仍可能存在，应以相册文件与错误信息一起核查。

### 现场怎么拍

固定为真实车头安装角度，先拍左右标识各一组由远到近的画面，再拍左右偏移、斜视、
暗光与反光。也拍没有标识的背景、蓝色色块、圆形蓝色物体、白色图案等负样本。
建议每个方向先收集 30～50 张有差异的画面，负样本至少 30 张，避免全是同一距离的连拍。
v1.5 已加入独立颜色模式；拍摄标签仍是人工备注，不能把标签选择当成程序预测结果。
相机如开启水平镜像，左右视觉会反转，必须核对画面中的箭头方向；默认镜像关闭。

### 第一版算法与边界

在完整 640×360 识别画面中找蓝色候选块 → 检查尺寸、宽高比和完整性 → 在内部椭圆区域取白色最大连通块
（排除外圈）→ 归一化到 24×24，与两张用户参考图提取的模板比较 IoU →
分数及左右差值均通过后，连续 4 帧确认。存在矛盾方向时拒绝判定。
同一标识只产生一次事件，离开画面至少 8 帧后再允许下一次。
IoU 是形状相似度，不是概率或识别准确率。

模板直接由用户给的两张照片提取，不需要 AI 模型文件。小目标、遮挡、明显旋转、
严重透视或曝光变化可能拒识，蓝色阈值和尺寸门限必须用 K230 实拍调参。
当前全画面搜索尚无赛道专用 ROI，不保证比赛可用距离、速度或帧率。
GPIO 默认关闭，当前 Ti60 接收端和 K230 发送端已经按固定 STB 协议对齐，
启用前须完成实物占用、电平和线束核对。发送失败时保持故障，不会自动重复旧事件。

## 调试顺序

1. 读取固件与现有文件信息，备份原有启动程序后再考虑修改。
2. 临时运行摄像头预览，确认方向、曝光及安装视野。
3. 用实际赛题标识和色块验证识别，之后确定前方标识区、侧方颜色区的 ROI。
4. 按固定四线表验证 STB 波形、编码和心跳，再接入 Ti60 状态机。
5. 台架验证后再保存为离线启动程序，最后做实车测试。

## 固定 GPIO 接口（替代旧 REQ/ACK 方案）

当前固定方案为 GPIO42/43/34/35 → Ti60 P4 pin28/33/34/39，详见文首固定接线说明。

| 信号 | K230 GPIO | Ti60 P4 | 方向 |
|---|---|---|---|
| DATA0 | GPIO42，K230排针1 | pin 28 / User_IO25 | K230 → Ti60 |
| DATA1 | GPIO43，K230排针2 | pin 33 / User_IO28 | K230 → Ti60 |
| DATA2 | GPIO34，K230排针8 | pin 34 / User_IO29 | K230 → Ti60 |
| STB | GPIO35，K230排针10 | pin 39 / User_IO34 | K230 → Ti60 |
| GND | K230排针4 | pin 30 | 共地 |

应用事件代码仍为1左、2右、3红、4绿、5蓝、6黄；驱动转换成 CAT/VAL 协议后发送。
每条消息发送 `(0,CAT,0,VAL,0)` 两遍，STB上升沿采样；没有ACK返回线。
接线编号固定，首次接线前核对实物方向、FPIOA占用并测量输出电平。
## 现场前视版

前视入口为 `field_startup.py`，装到 SD 卡根目录时命名为 `main.py`。
`field_vision.py` 在一帧里运行转向牌识别和四色方块跟踪。画面供调试观察，循迹和转向执行由 Ti60 的红外循迹与状态机负责。

- 转向牌沿用 640×360 识别和连续 3 帧确认。K230 发一次方向，Ti60 先锁存；宽黑后丢线时才消费请求，12 秒未到岔口则过期。宽黑门槛和转向时长仍需在实车岔口确认。
- 色块在画面下方识别，须先稳定确认、向右推进，再在右沿到达画幅 98% 附近后持续至少两帧。边缘裁切的目标沿用已确认的颜色，画面共同横跳时暂停计数。每个物理目标只记录一次。
- 保持 GPIO42/43/34 和 GPIO35 STB 的固定接线。启动器启用 GPIO，并保留引脚复用检查。SD 分析日志优先存到 `/data/field_vision_runs`，不可用时用 `/sdcard/field_vision_runs`。
